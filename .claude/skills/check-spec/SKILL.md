# 仕様書エラーチェック：$ARGUMENTS

## 絶対に守ること
- **`specs/` のファイルは変更・削除・追加・リネームしない。**（フックでもブロックされる）
- **確認一覧の「修正内容」列は書き換えない。** ユーザーが書く仕様書の付属情報である。（フックでもブロックされる）
- 不備を推測で補って「問題なし」にしない。
- このスキルではコード（`app/`）を作らない。

## 確認一覧ファイル
- 場所：`spec-reviews/<仕様書のファイル名>.md`（例：`specs/SCR-01_qa.png` → `spec-reviews/SCR-01_qa.md`）
- 無ければ `spec-reviews/_template.md` をもとに作る。
- 列：`No | 重大度 | チェックID | 箇所 | 不備の内容 | 実装時の扱い | 修正提案 | 修正状態 | 修正内容`
- 修正状態の遷移（AI が変更してよいのは ★ だけ）

```
未修正 ──(ユーザーが修正内容を記入)──▶ 修正済AI未確認 ──★AI確認──▶ AI確認OK（確定。以後チェックしない）
                                              └────★AI確認──▶ AI確認NG ──(ユーザーが再記入)──▶ 修正済AI未確認
```

## 手順
1. **対象を決める**：`$ARGUMENTS` があれば `specs/` 内のそのIDで始まる PNG、無ければ `specs/` の PNG すべて。
2. **確認一覧を読む**：既存の行を状態ごとに扱う。
   - `AI確認OK`：**再チェックしない。** 「修正内容」を仕様書の付属情報として、仕様書と同じ扱いで以降の判定に使う。
   - `修正済AI未確認`：手順4で確認する。
   - `未修正`・`AI確認NG`：そのまま残す（変更しない）。
3. **画像を読み、チェック項目で判定する**（下表）。仕様書の画像と AI確認OK の付属情報を合わせて判定する。
   - 既存の行と同じ「チェックID＋箇所」の不備は追加しない。
   - 新しい不備は、末尾に次の No で追加する（修正状態 `未修正`、修正内容は空欄）。
4. **修正内容を確認する**（`修正済AI未確認` の行）。次をすべて満たせば `AI確認OK`、1つでも満たさなければ `AI確認NG`。
   - 不備の内容を解消している（例：C04 なら表示する文言そのものが書かれている）
   - 実装できる具体さがある（「いい感じに」「検討中」などは NG）
   - 仕様書の画像、他の AI確認OK の付属情報と矛盾しない
   - NG のときは「修正提案」を **NG の理由と、何を書けばよいか** に更新する（先頭に `【NG】` を付ける）。
5. **表の外を更新する**：「最終チェック」の日付、「集計」、「実装可否」。
6. **報告する**：チャットには、ファイルごとの集計、今回の変更（追加した行、OK／NG にした行と理由）、実装可否だけを短く示し、詳細は確認一覧ファイルへのリンクで案内する。最後に「仕様書は変更していません」と書く。

## チェック項目

| ID | 観点 | 不備とする条件 | 重大度 |
|---|---|---|---|
| C01 | 画面識別 | ファイル名の画面ID（SCR-xx）と画面名が対応しない／画像内に画面名が無い | 警告 |
| C02 | 項目定義表 | No / 項目 / 種別 / 仕様 の表が無い | 警告 |
| C03 | 種別 | 種別が書かれていない、または `.claude/rules/material-design.md` の対応表に無い種別 | 警告 |
| C04 | 文言の欠落 | 表示すべき文言が無い（例：回答文・ラベル・エラーメッセージが空） | エラー |
| C05 | 判読不能 | 文字がつぶれている・途切れている・隠れていて読めない | エラー |
| C06 | 状態の未定義 | 1つの状態しか描かれておらず、他の状態（初期表示・開閉・空・エラー・ロード中など）が不明 | 警告 |
| C07 | 振る舞いの未定義 | ボタン・リンク等の操作結果（遷移先・活性条件・入力チェック）が書かれていない | エラー |
| C08 | 矛盾 | 画像内の記述どうし、付属情報、または他の仕様書と食い違う | エラー |
| C09 | 参照先不明 | 仕様書に存在しない画面・要素を参照している | 警告 |
| C10 | 見た目の指定 | 配色・装飾が描かれている（ハーネスでは参考扱いになることを周知） | 情報 |

- ハーネスのルールで扱いが決まっている不備も省かない。「実装時の扱い」欄にルールの扱いを書く。
- 重大度は `エラー`／`警告`／`情報` の文字だけを書く（装飾しない）。

## 実装可否の判定
- 重大度エラーの行がすべて `AI確認OK` →「実装可」
- それ以外 →「仕様確認が必要」。実装時（`app/` への書き込み時）に「エラーの項目が修正されていません。本当に修正しますか？」の確認が出る。
